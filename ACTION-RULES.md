# Action rules

These rules say how MentorAgent decides which methods of your application become actions, what they are
called, and how roles and confirmations add up. They describe what the library does today.

- Every rule has a stable name and at least one test that fails if the library stops following it.
- A rule changes only with a note in the [CHANGELOG](CHANGELOG.md), and the table says in which version
  it changed.
- A name is never reused. A rule that is dropped stays in the table, marked "retired in x.y.z".

## Areas

The first part of each name is its area:

- `scan`: which methods become actions;
- `fluent`: the actions an application registers in code, with `MentorOptions.Actions`;
- `kind`: the kind of class they belong to (the coordinator's actions, a specialist, a skill, a team);
- `name`: the names the model sees;
- `enabled`: whether an action is on: shipped off in the code, turned on or off from outside it;
- `confirm`: when an action asks the user to confirm;
- `roles`: who may run an action;
- `policy`: what the action policies (`IMentorActionPolicy`) decide about what an agent is offered;
- `describe`: the description the model reads for an action;
- `declarative`: the actions a definition file (`Novior.MentorAgent.Declarative`) gives its agent;
- `surface`: what is published on `/mcp` and on the A2A card;
- `page`: the UI actions a page declares, and what the catalogue's trace keeps of them;
- `endpoint`: the application's endpoints declared as actions (Novior.MentorAgent.Server);
- `candidate`: the AutoMentor's candidates, found in the perimeter the code declares;
- `team`: the teams an `IMentorTeamSource` gives, and what their members may call;
- `skill`: which skill the assistant gets when two have one name;
- `mcp`: the tools of the MCP servers the application consumes.

## How confirmations and roles add up

- A confirmation is asked only when `RequireConfirmation` is on and at least one source wants it: what
  the action declares, the default for writes, or `RequiresApproval`. With a governor, its answer replaces these
  sources (`confirm.external-decides`).
- Roles and confirmation both apply, and roles come first: a user without the role is refused before
  anyone is asked to confirm.

## The rules

|---|---|---|---|
| `scan.assemblies-once` | Each assembly in `ScanAssemblies` is read once. An assembly listed twice is read once, with a warning that names it. | 1.3.0 | |
| `scan.concrete-classes` | Only classes that are not abstract are read. Abstract classes, structs and interfaces give no action. | 1.3.0 | |
| `scan.public-instance-declared` | Only public instance methods declared on the class itself become actions. Static, internal, protected and private methods do not, and a method the class inherits is an action of its base class only. | 1.3.0 | |
| `scan.marker` | A method becomes an action with `[MentorAction]`, whatever its `Description`, or with a `[Description]` whose text is not blank. With neither, it is not an action. | 1.3.0 | |

| `scan.override-keeps-action` | An override of an action is an action of the class that overrides it, with what the base method declares: `[MentorAction]` and `[Description]` both pass to the override. | `fluent.coordinator-action` | A method registered in `MentorOptions.Actions` is one of the coordinator's actions, named by `name.snake-case`, or by the name its registration declares with `Name`. | `fluent.method-must-exist` | A registration names one public instance method declared on a concrete class itself, not generic, and the only public method with that name. Otherwise the application stops when it starts, naming the method. | 1.4.0 | |
| `fluent.declared-decides` | A registered action gets what its registration declares: description, confirmation, read-only, roles, on or off, category, hint and page. Without a declared confirmation, `confirm.default-for-writes` applies, as to a `[MentorAction]` method. | 1.4.0 | |
| `fluent.description-required` | A registration without a description stops the application when it starts. | 1.4.0 | |
| `fluent.no-double` | A method is registered once. A method that is already an action by its attributes, in an assembly of `ScanAssemblies`, cannot be registered too: the application stops when it starts, naming it. | 1.4.0 | |
| `fluent.command` | A command registered with `MentorOptions.Actions.AddCommand` is one of the coordinator's actions, named after its type by `name.snake-case`, or by `Name`. Its parameters are the type's public properties: a call builds the type from the model's arguments and gives it to the handler's `HandleAsync`, and arguments that do not make one fail the call. It is a write: without a declared confirmation `confirm.default-for-writes` applies. The same roles, confirmations, governor, policies, `/mcp`, A2A card and team members apply to it as to a method registered in code; a handler that returns a result gives it to the model. | 1.4.0 | |
| `fluent.query` | A query registered with `MentorOptions.Actions.AddQuery` is one of the coordinator's actions, named and built as a command is, and always read-only: the model reads what its handler returns. | 1.4.0 | |
| `fluent.message-checked` | A command or a query that cannot be sent stops the application when it starts, naming the type: a type that is not a class, a record or a struct with properties; a handler that is not a concrete class, or does not implement the handler's interface for the type exactly once; no description; a command declared read-only; a name that is not a tool name; the same type registered twice; a name another registration of `MentorOptions.Actions` has. | 1.4.0 | |
| `fluent.message-trace` | `IMentorActionCatalog.GetRegistrations()` lists one registration per command or query: `Origin` `command` or `query`, `Id` `<origin>:<type>`, `Source` the type's full name. In `GetActions()` its action has the same `Origin` and `RegistrationId`, and `Method` is the handler's `HandleAsync`. | 1.4.0 | |
| `scan.controllers-are-endpoints` | A controller is not read by the scan: a class that derives from `ControllerBase`, or carries `[Controller]` or `[ApiController]`, and not `[NonController]`. A `[MentorAction]` on a controller's action is read from its endpoint (`endpoint.declared`), where its authorization and filters run. Up to 1.3.0 the scan read it and the action called the method on an instance from the container. | 1.4.0 | |
| `scan.attributes-not-created` | The scan reads which classes are controllers, and which roles a candidate's `[Authorize]` and `[AllowAnonymous]` give, from the attributes' metadata: it creates no attribute of the application but those two, so an attribute whose constructor throws does not stop the application. A class whose attributes name a type that does not load is skipped, and a warning names it; a candidate method whose attributes cannot be read is no candidate. From 1.4.1 a method, or a team member's property, whose attributes name a type that does not load is skipped too, with a warning that names it, and the rest of the class stays. | 1.4.0 | |
| `kind.one-per-class` | A class is of one kind only, in this order: `[MentorTeam]`, then `[MentorAgent]`, then `[MentorSkill]`, then a plain class whose methods are the coordinator's actions. | 1.3.0 | |
| `kind.page-is-separate` | `[MentorPage]` records the page and does not change the class's kind. Its methods follow the other rules. | 1.3.0 | |
| `kind.agent-owns-methods` | The methods of a `[MentorAgent]` class are that specialist's own actions, not the coordinator's. | 1.3.0 | |
| `kind.skill-methods-level1` | The methods of a `[MentorSkill]` class are the coordinator's actions, registered once. A skill with no methods gives none. | 1.3.0 | |
| `kind.team-needs-members` | A `[MentorTeam]` class with no `[TeamMember]` property is left out, with a warning. | 1.3.0 | |
| `kind.member-tools-leave-level1` | A class listed in a `[TeamMember(Tools = …)]` is that member's toolbox. Its methods are not the coordinator's actions, and they are not on `/mcp` or the A2A card. A `[MentorSkill]` class keeps its methods as the coordinator's. | 1.3.0 | |
| `kind.member-tools-same-rules` | A member's tool classes follow the `scan.*` rules, and each tool keeps what its attribute declares. | 1.3.0 | |
| `name.snake-case` | An action is named after its method. A trailing `Async` (exact case) is dropped, then the name becomes snake_case: every capital letter starts a new word (`GetHTTPStatus` becomes `get_h_t_t_p_status`), spaces and dashes become underscores, and digits stay. | 1.3.0 | |
| `name.team-tool` | A team is offered to the coordinator as one tool, named after the team's `Name` by the same rule (`Business Analysis Team` becomes `business_analysis_team`). | 1.3.0 | |
| `name.shared-warned` | Two methods with the same action name, compared without regard to case, are named in a warning at startup. One method found twice is not two. | 1.3.0 | |
| `name.called-method-decides` | When methods share a name, the roles, the confirmation, its text and the page to open are those of the method actually called (BUG-188). | 1.3.0 | |
| `enabled.off-by-default` | An action declared `[MentorAction(Enabled = false)]`, or one MentorAgent registers off, is in the catalogue (`EnabledByDefault` false) and nowhere else. It is offered to no agent, described to no model, not listed on `/mcp` and not on the A2A card, and a call to it does not run (`Denied`, `disabled`), until an `IMentorActionGovernor` turns it on. | 1.3.0 | |
| `enabled.external-decides` | With an `IMentorActionGovernor` registered, its answer turns an action on or off, and `null` leaves the code's word. It is asked once as a session builds its tools (the coordinator's, the specialists', the team members'), on every `tools/list` of `/mcp`, and before every call, ahead of the roles. A session keeps the tools it was built with, and a call to an action turned off meanwhile is refused. A governor that throws, or does not answer within `ActionPolicyTimeout`, stops the action (`PolicyFailed`, `governor-failed`). There can be one: a second registration throws. | 1.3.0 | |
| `confirm.declared-decides` | An action that writes `RequiresConfirmation`, `true` or `false`, gets what it declares. | 1.3.0 | |
| `confirm.default-for-writes` | A `[MentorAction]` that does not write `RequiresConfirmation` asks for confirmation when `RequireConfirmationForWrites` is on (the default), unless it only reads: `ReadOnly = true`, or `IsReadOnlyAction` says so. | 1.3.0 | |
| `confirm.description-only-not-defaulted` | A method marked with `[Description]` alone never asks for confirmation by default. The startup warning lists it as not covered. | 1.3.0 | |
| `confirm.predicate-adds` | When `RequiresApproval` returns true for an action's name, the action asks for confirmation; the predicate is asked again at every call. Returning false never takes away a confirmation the action declares; the governor can (`confirm.external-decides`), and it can take away the predicate's too. | 1.3.0 | |
| `confirm.master-switch` | With `RequireConfirmation` off, no action of the application asks for confirmation, whatever it declares. The approval a hosted MCP server asks for comes from the provider and is still shown (BUG-137). | 1.3.0 | |
| `confirm.beats-read-only` | An action that asks for confirmation is not read-only, whatever `ReadOnly` or `IsReadOnlyAction` say. | 1.3.0 | |
| `confirm.unconfirmed-writes-warned` | At startup a warning names the writes that run without confirmation, in two lists: the `[MentorAction]` methods that opt out, and the methods marked with `[Description]` alone. | 1.3.0 | |
| `confirm.external-decides` | With an `IMentorActionGovernor` registered, its answer decides whether a call is confirmed, in place of the code's: `Required` asks even if the code does not, `None` does not ask even if the code does (declared, by default for writes, or by `RequiresApproval`), and `Code` leaves the code's word. Narrowing takes effect at once: a confirmation added counts from the call, as an action turned off does. Widening counts from the next session: a confirmation taken away, as an action turned on. A call is confirmed when the session's answer or the call's asks for it. In Native mode no auto-approval rule lets through a confirmation the governor requires: those rules are the code's. It does not take away an `IMentorActionPolicy`'s `Confirm` nor a hosted MCP server's approval, and with `RequireConfirmation` off nobody is asked. An action whose confirmation is taken away still counts as one that changes data. The decisions say when the governor changed whether a call is confirmed (`ConfirmationFromOutside`). | 1.3.0 | |
| `roles.any-of` | An action with `RequiredRoles` runs for a user who holds any one of them, checked with `ClaimsPrincipal.IsInRole` (role names are case-sensitive). With no roles there is no check. | 1.3.0 | |
| `roles.signed-in` | An action with `RequiredRoles` needs a signed-in user. With no `AuthenticationStateProvider`, or nobody signed in, it is refused. | 1.3.0 | |
| `roles.checked-before-confirmation` | Roles and confirmation both apply. Roles are checked first, so a user without the role is never asked to confirm (BUG-063), and checked again when the confirmation comes back. Turning confirmations off does not turn the role check off. With a governor, the roles checked are the ones it gives (`roles.external-replace`). | 1.3.0 | |
| `roles.offered-when-allowed` | The model is offered only the actions the user's roles allow, at every level. An action left out is still refused if it is called. | 1.3.0 | |
| `roles.external-replace` | With an `IMentorActionGovernor` registered, the roles it gives an action replace the code's. `null` leaves the code's, and an empty list requires none. They decide the offer (once, as a session builds its tools, at every level) and every call, checked against the governor's answer at the call, before the confirmation and again after it. On `/mcp` they decide which callers see and call the action, by the rule of the code's roles: an action withheld only for its roles is published once the governor requires none. The decisions say so (`RolesFromOutside`). | 1.3.0 | |
| `policy.offered-to-agents` | When the application registers action policies, every agent of the turn is offered only the application's actions they allow, as of 1.3.1: the coordinator's are asked about at the start of the turn, and those of a specialist, a team member (written in C#, given by an `IMentorTeamSource` or read from a `*.team.yaml` file) and an agent of an `IMentorAgentSource` at the agent's first request, once a turn for each tool: `IsAllowedAsync` at `Offer`, with the agent's `AgentKind` and `AgentName` (a team member's role, none for an agent source). One that a policy does not allow, or whose policy fails, is left out of that agent's requests and of a team member's instructions. A call to it anyway reaches the gate, which refuses it without asking the policies about the call (`Denied`, `not-offered`); another agent of the turn that was offered it still runs it. MentorAgent's own tools are never asked about; a page's UI actions are, one by one (`page.offered`). Without a policy nothing is asked. | 1.4.0 | |
| `describe.external-replace` | With an `IMentorActionGovernor` registered, the description it gives an action replaces the code's in what a model reads: the tools of the coordinator, the specialists and the team members, the texts tool filtering ranks, and the MCP server's `tools/list`. `null` or a blank text leaves the code's. The action's name and argument schema never change, and the code's `ProactiveHint` still follows the description. It is asked once as a session builds its tools, and on every `tools/list`, never at a call. What the user sees keeps the code's description: the confirmation banner, the bar of the running action and the decisions' `DisplayName`. On a call to `/mcp` the policies are asked with the code's description. The A2A card, `IMentorActionCatalog` and the onboarding tour follow the code. | 1.3.0 | |
| `declarative.functions-match` | A `kind: function` entry of a definition reaches its agent only if the session has an action of that name. A name the application does not have, or an action that is off for the session, is taken away with a Warning and reported as a tool left out (`tool-not-found`), and the agent loads without it: an action that is off is described to no model through a definition that names it. | 1.3.0 | |
| `declarative.no-hosted-tools` | A definition cannot add a tool of its own. `webSearch`, `codeInterpreter`, `fileSearch` and `mcp` entries are taken away with a Warning and reported (`hosted-tool-removed`), and the agent loads with the application's own tools. If they cannot be taken away, the agent is not loaded (`foreign-tools`). | 1.3.0 | |
| `surface.coordinator-only` | `/mcp` and the A2A card publish only the coordinator's actions, never a specialist's or a team member's. | 1.3.0 | |
| `surface.mcp-withholds-gated` | `/mcp` does not publish an action that asks for confirmation, whether it is declared, by default or by `RequiresApproval`. With a governor, an action that asks for confirmation is published once the governor takes the confirmation away, and one it requires a confirmation for is withheld (`confirm.external-decides`). An action with roles is published only with `McpCallerPrincipal`, to the callers who hold one of its roles. An action that is off is not published, unless the governor turns it on for the request (`enabled.external-decides`). | 1.3.0 | |
| `surface.card-ungated-only` | The A2A card lists only the coordinator's actions that ask for no confirmation (declared, by default or by `RequiresApproval`), need no role, and whose class the application's container can create (BUG-177). A name that two actions share is left off when either of them is gated. The card follows the code only: an action shipped off is not on it, and one the governor turns on is not added. | 1.3.0 | |
| `surface.governor-session` | The governor is asked with the session's id (`MentorActionRequest.SessionId`) on every surface, the same id the gate's decisions carry. On `/mcp` it is a fingerprint of the MCP session, never the id. | 1.3.0 | |
| `page.gated` | On Path A a page's UI action is a tool of the coordinator's run, and the gate decides it like every other action: the action policies and their before-action hook are asked, the observers receive its decisions with its description as `DisplayName`, it gets a span and Stop reaches it. It asks for no confirmation of its own and needs no role; a policy can stop it or ask for a confirmation. On the hub the client receives `UIActionRequested` only for an action the gate let through. | 1.4.0 | |
| `page.kind` | Every `MentorActionRequest` and `MentorActionDecision` says the kind of the action, `Kind`: `UI` for a UI action the page declared, `Server` for every other; and `PageName`, the page the user is on, which for a UI action is the page that declared it. A UI action is never one of the application's actions, even with the name of one the session does not offer (off, or left out by the governor): that action's roles, confirmation, governor and description do not apply to it, and a banner a policy asks for shows the UI action's own text. | 1.4.0 | |
| `page.offered` | When the application registers action policies, each UI action of the page now shown is asked about at the start of the turn, as the application's actions are: `IsAllowedAsync` at `Offer`, with `Kind` `UI`, the page's name, no roles and no confirmation. One that a policy does not allow, or whose policy fails, is left out of every request of the turn, and so is one of a page a call of the run opens, asked about when it opens — with the page's name, even when its actions have the names of the page left. One left out stays out for the rest of the turn, on every page: an action the policies do not offer on the page left is not offered on the page now shown either, until the next turn. A call to it anyway reaches the gate, which refuses it without asking the policies about the call (`Denied`, `not-offered`). Without a policy nothing is asked and every UI action is offered. | 1.4.0 | |
| `page.left-not-offered` | `navigate_to` to a page other than the one shown, and an action whose `NavigateTo` opens another page, take the UI actions of the page being left back before they ask for the navigation: the next request of the turn offers only the actions the page now shown registers, none for a page without UI actions, and a call to one of the page left all the same runs nothing. `navigate_to` to the page shown changes nothing. Only in a turn with a Blazor circuit: over the hub, SSE and A2A the page's actions come with the client's snapshot, and the next turn brings the new page's. | 1.4.0 | |
| `page.trace-names-only` | `IMentorActionCatalog.GetRegistrations()` lists, after the registrations of the code, one registration per page that declared UI actions: `Origin` `page`, `Id` `page:<page>`, `Source` and `Page` the page's name. It keeps the names of the actions only, never a description, a parameter hint or a handler: a page declares them from the browser. A page's UI actions are not in `GetActions()`. | 1.4.0 | |
| `page.union-since-start` | A page lists every name its pages declared since the application started, in every session, in the order first seen; an action a page drops stays listed. One counter of the process grows at every change, a name or a rejection the page did not list before, and the page takes its value as `Revision`. The same declaration made again changes nothing. The registrations of the code have `Revision` 0. | 1.4.0 | |
| `page.name-shape` | The trace lists an action name made of letters A-Z and a-z, digits, `_` and `-`, from 1 to 64 of them, as a model's tool name. Another is in the page's `Rejected` with this rule, cut to 64 characters, a control or format character written as U+FFFD. A page name has from 1 to 128 characters, spaces included, is not white space only and has no character of Unicode category C (control, format, a lone surrogate, private use, unassigned; so no line break or tab). A page without a name, or with another one, is not listed, and a warning in the log says so once, without the name. | 1.4.0 | |
| `page.limit` | The trace lists 64 actions per page (`MentorPageActionLimits.MaxActionsPerPage`): the ones after are in the page's `Rejected` with this rule. It lists 200 pages (`MaxPages`): a page after them is not listed, and a warning in the log says so once. A page writes down 64 rejections at most (`MaxRejectedPerPage`). These limits are the trace's only: the actions a page offers the model are not cut by them. | 1.4.0 | |
| `endpoint.declared` | An endpoint is one of the coordinator's actions when it is declared with `WithMentorAction(…)` on its route builder (a minimal API, a group, a controller's route) or with `[MentorAction]` on a controller's action, in a host with `AddMentorAgentServer()`. The endpoints are read once the host has started. The application stops when it starts, naming the endpoint, when a declared endpoint: has no description; answers more than one verb, or every verb; has a lambda as its handler and no name (`WithMentorAction(name, …)` or `WithName(…)`); is given a name that is not a tool name (letters, digits, `_` and `-`, up to 64); has the name of another action, or of another endpoint's action; reads a header, a form, a file or `[AsParameters]`, or more than one body; has an authorization that names a policy not registered. The name is the one declared, then the endpoint's name, then its handler's method, by `name.snake-case`. The model gives the route values, the query values and one JSON body; services, `HttpContext`, `ClaimsPrincipal` and the cancellation token are not in what it reads. | 1.4.0 | |
| `endpoint.authorization-first` | The action runs the endpoint as the user of the turn, after the endpoint's authorization as `UseAuthorization` decides it: its `[Authorize]`, its policies, the fallback policy, `[AllowAnonymous]`. The authentication schemes a policy names are not run again: the user is the turn's. A user who is refused gets no call to the endpoint: the action fails with 401 (not signed in) or 403 (not allowed), and the model reads why. An endpoint that asks for authorization in a host without it is refused. The action policies, the governor, the roles and the confirmation of the gate come before, as for every action. | 1.4.0 | |
| `endpoint.runs-the-pipeline` | The action runs the endpoint itself, in the process, in a scope of its own: its request delegate, so its filters, its binding and its validation, the MVC pipeline of a controller. The application's middleware does not run: what comes before routing (rate limiting, CORS, headers, exception pages) is not there. An answer of 400 or more is a failed action, with the status and the beginning of the body for the model; the model reads at most 16,000 characters of an answer. | 1.4.0 | |
| `endpoint.verb-default` | Without a declared confirmation, a `GET` or `HEAD` endpoint only reads, and an endpoint of another verb writes: `confirm.default-for-writes` applies to it. `ReadOnly()` and `IsReadOnlyAction` say it only reads, and a declared confirmation wins. | 1.4.0 | |
| `endpoint.not-published` | An endpoint's action is not published on `/mcp` nor on the A2A card: an MCP caller is not the user of the turn the endpoint's authorization is decided for. In the catalogue its `McpExposure` is `NotServed` and `OnAgentCard` is false. | 1.4.0 | |
| `endpoint.roles-from-authorization` | An endpoint's action takes its `RequiredRoles` from the endpoint's authorization, combined as `UseAuthorization` combines it: its `[Authorize]` (of the class and of the method), its policies by name and built in place, the fallback policy when the endpoint says nothing; none with `[AllowAnonymous]`. The roles of its one role requirement are the action's, any one of them (`roles.any-of`), so the `roles` rules apply: the action is offered only to a user who holds one, and refused before any confirmation to one who does not. Several role requirements ask for roles together, which an action's roles cannot say: the action takes none from them, an information line in the log names the endpoint, and the endpoint still refuses the call (403). Other requirements (claims, assertions, a signed-in user) give no roles: the endpoint decides them at the call. Roles declared with `RequireRoles(…)` or `[MentorAction(RequiredRoles = …)]` replace the ones of the authorization. | 1.4.0 | |
| `candidate.opt-in` | MentorAgent looks for candidates only with `AutoMentor.Enabled`, off by default, and only in the namespaces of `AutoMentor.Namespaces`. With no namespace there is no perimeter and no candidate, and a warning in the log says so. | 1.4.0 | |
| `candidate.in-perimeter` | A candidate's class is public, concrete and not generic, in an assembly of `AutoMentor.Scan` (empty: `ScanAssemblies`), in one of `AutoMentor.Namespaces` or under it (`Shop.Services` covers `Shop.Services.Orders`, not `Shop.ServicesLegacy`). Never one of MentorAgent's own assemblies, a controller (its actions are endpoints), a class with `[MentorAgent]`, `[MentorTeam]` or `[MentorSkill]`, a team member's toolbox, a component, or a class the compiler generates. | 1.4.0 | |
| `candidate.shape` | A candidate is a public instance method its class declares: not an accessor or an operator, not one of `object`'s nor one the compiler generates, not generic, without `ref`, `out` or pointers. The others are not listed in the trace. | 1.4.0 | |
| `candidate.excluded` | `[MentorExclude]` on a class (and the classes derived from it) or on a method keeps it out, and out of the trace: a name excluded on purpose does not leave the code. | 1.4.0 | |
| `candidate.not-yet-an-action` | A method that is already an action, by `[MentorAction]`, `[Description]` or `MentorOptions.Actions`, is not a candidate: it keeps its own registration. | 1.4.0 | |
| `candidate.di-resolvable` | A candidate's class is one the application's container gives for the class itself (`IServiceProviderIsService`). The methods of another class are in its registration's `Rejected` with this rule. | 1.4.0 | |
| `candidate.schema` | A candidate's tool is built as every action's is, with its parameters described in JSON Schema. A method whose tool cannot be built is in `Rejected` with this rule. | 1.4.0 | |
| `candidate.name` | A candidate's name is its method's, in snake_case (`name.snake-case`).
